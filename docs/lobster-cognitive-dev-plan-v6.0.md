## 一、项目背景与核心命题

### 1.1 现状

深度龙虾Ai 经过 v2.0 至 v5.0 的五轮迭代，**iOS 端已完成全部 14 项元认知与自适应思维能力 + 三档强度分级系统**，在"像 TRAE 一样思考"的结构化程度上达到 90% 以上。

然而，**Android 端深度模式相关功能完全空白**——既没有 Workflow 状态机、GoalRunner 自动续跑等基础架构，也没有 14 项认知能力的任何实现，深度模式 UI 入口也不存在。两平台之间存在巨大的功能鸿沟。

### 1.2 核心命题（v6.0）

**实现 iOS / Android 双端深度模式功能对齐**，让 Android 用户也能享受到完整的深度龙虾Ai 认知能力。同时，针对 Android 平台特性（设备碎片化、后台限制、内存约束）做适配优化，确保深度模式在 Android 上的可用性和稳定性。

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 移植能力 | **14/14 + 3档** | 6 大维度元认知能力 + DeepModeLevel 三档强度 |
| 架构对齐 | **3 个核心模块** | GoalRunner + WorkflowPhase + SequentialThinkingTool |
| 新增阶段 | **4 个阶段** | A（基础架构）/ B（P0+P1）/ C（P2+分级）/ D（子智能体） |
| 硬约束 | 2 个 | 功能对齐 iOS + Android 平台特性适配 |
| 预期工期 | **6-8 周** | 四阶段递进式推进 |

### 2.2 Agent Loop 结构详解

**核心入口**：`ChatViewModel.runAgentLoop()`

**执行流程**：
```
sanitizeAgentHistory()  // 历史清洗
    ↓
offloadContextIfNeeded()  // 上下文管理
    ↓
currentProvider.streamMessage()  // 流式请求
    ↓
chunk processing (Text/Thinking/ToolCall/...)  // 分块处理
    ↓
executeTools()  // 顺序执行工具调用
    ↓
append tool_results to history  // 结果回写
    ↓
next turn (or break if no tool_calls)
```

**关键特性**：
- 单 turn 内 in-loop compact：上下文膨胀时自动压缩，不消耗 turn 配额
- 空 turn 自愈：工具结果后收到空回复时，自动注入 system-reminder 并重试
- 队列中断：用户发新消息时，在当前工具完成后中断循环
- 工具输入去重：重复 tool_call_id 自动重命名，防止上游网关异常

**工具执行方式**：**纯串行 for 循环**
- 无并行工具执行能力
- 代码中多处 "Mirrors iOS ConcurrentTools" 注释，表明有意识对齐但未实现

### 2.3 记忆系统现状

**存储方式**：文件系统（Markdown 文件）
- `GLOBAL.md` — 全局记忆（用户维护，agent 只读）
- `YYYY-MM-DD.md` — 每日日志（agent 写入）

**检索方式**：
- 行级关键词模糊匹配（ALL 关键词必须匹配）
- ±2 行上下文窗口
- 30KB 硬上限 / 30 天回溯

**缺失**：
- 无结构化分类（偏好/规则/事实/项目上下文）
- 无 DeepModeRule 机制
- 无 StructuredMemoryStore 对应物

### 2.4 UI 层现状

**ChatScreen.kt**（~6500+ 行）结构：
```
TopAppBar (标题/模型/菜单)
    ↓
LazyColumn (消息列表)
├── UserMessage
└── AssistantMessage
    ├── Text blocks (Markdown)
    ├── Thinking blocks (可折叠)
    └── ToolCallPill (工具胶囊)
    ↓

    ↓
Composer (输入框 + 斜杠菜单)
    ├── /model, /thinking, /memory, /clear...

```

**深度模式 UI**：完全缺失
- 无深度模式开关
- 无 Workflow 阶段指示器
- 无 DeepModeLevel 选择器
- 无认知负荷监控 UI

| 维度 | iOS | Android | 差距等级 |

| 并行工具执行 | ✅ 有 | ❌ 串行 | 🟡 重要 |
| 14 项认知能力 | ✅ 14/14 | ❌ 0/14 | 🔴 核心 |
| 三档强度分级 | ✅ 有 | ❌ 无 | 🔴 核心 |
| 子智能体系统 | ✅ 有 | ❌ 无 | 🔴 核心 |
| 结构化记忆 | ✅ 有 | ⚠️ 基础版 | 🟡 重要 |
| 深度模式 UI | ✅ 完整 | ❌ 无 | 🔴 核心 |
| 工具系统 | ✅ 对齐 | ✅ 对齐 | 🟢 一致 |
| Thinking 系统 | ✅ 对齐 | ✅ 对齐 | 🟢 一致 |
| MCP / Skills | ✅ 对齐 | ✅ 对齐 | 🟢 一致 |

### 3.2 三大核心缺口详解

#### 缺口 1：GoalRunner 自动续跑机制

**iOS 端**：GoalRunner 监控任务进度，达到 turn 上限后自动判断是否需要续跑，实现长任务的自动推进。

**Android 端**：MAX_AGENT_TURNS = 200，达到上限后停止，等待用户手动点击 "Continue" 调用 `resume()`。

**移植必要性**：🔴 必须
- 深度模式的核心就是"长链路深度思考"，没有自动续跑等于深度模式残废
- 用户不可能守在屏幕前点几十次 Continue

#### 缺口 2：WorkflowPhase 状态机

**iOS 端**：WorkflowPhase 枚举管理 idle → planning → executing → verifying 等阶段，驱动 UI 可视化和阶段门控。

**Android 端**：无状态机，agent loop 自由流转，无阶段概念。

**移植必要性**：🟡 重要但非阻塞
- P0/P1 能力可以在无状态机情况下工作（纯提示词注入）
- 但 P2 能力（如 C9 认知负荷监控、C10 动态自主性）依赖阶段信息
- UI 可视化需要状态机驱动

#### 缺口 3：SequentialThinkingTool

**iOS 端**：SequentialThinkingTool 是深度思考的核心载体，模型可以主动调用进行结构化思考。

**Android 端**：无此工具，思考仅通过模型内置 reasoning 能力。

**移植必要性**：🔴 必须
- C11 按需顺序思考工具是 P2 档核心能力
- 多路径规划、根因分析等依赖结构化思考工具
- 三档分级中"高档"的核心体验差异点

## 五、阶段 A：基础架构补齐（地基工程）

> **目标**：把 Android 端的 agent 架构拉到和 iOS 相同的"地基"水平，为后续深度模式移植扫清障碍。

### A.1 GoalRunner 自动续跑机制

**新建文件**：
- `agent/GoalRunner.kt` — 目标运行器

**核心功能**：
1. 监控 agent loop 是否因 MAX_AGENT_TURNS 停止
2. 自动判断任务是否完成（解析模型输出的目标状态）
3. 未完成则自动调用 `resume()` 继续执行
4. 续跑次数限制（防止无限循环，默认 10 次）
5. 续跑状态持久化（DB 存储，应用重启可恢复）

**改动位置**：
- `ChatViewModel.kt` — `runAgentLoop()` 尾部集成
- `ChatSessionEntity` — 新增 `goal_runner_state` 字段

**关键设计**：
```kotlin
data class GoalRunnerState(
    val isActive: Boolean = false,
    val currentGoal: String? = null,
    val resumeCount: Int = 0,
    val maxResumes: Int = 10,
    val lastResumeAt: Long? = null,
)

// GoalRunner 解析模型输出的目标状态标记
// <<GOAL_STATE>> completed: <summary>
// <<GOAL_STATE>> need_more_context: <reason>
// <<GOAL_STATE>> in_progress: <current_step>
```

### A.2 并行工具执行（ConcurrentTools）

**新建文件**：
- `agent/ConcurrentTools.kt` — 并行工具执行器

**核心功能**：
1. 分析同一 turn 内的多个 tool_calls，判断哪些可以并行执行
2. 使用 Kotlin 协程 `async/await` 并行执行独立工具
3. 有依赖关系的工具保持串行执行
4. shell_execute 的沙箱并发限制处理

**改动位置**：
- `ChatViewModel.kt` — 工具执行循环替换为并发调度
- `ToolLoopDetector` — 适配并行执行的循环检测

**并行策略**：
- file_read / file_write / file_edit：同文件串行，不同文件并行
- shell_execute：默认串行（沙箱限制），特殊情况可配置并行
- browser_use：串行（浏览器实例共享）
- memory_write / memory_get：可并行
- read_image：可并行

### A.3 WorkflowPhase 状态机

**新建文件**：
- `agent/WorkflowState.kt` — 工作流状态机

**阶段定义**：
```kotlin
enum class WorkflowPhase {
    IDLE,           // 空闲
    PLANNING,       // 规划中
    EXECUTING,      // 执行工具
    VERIFYING,      // 验证结果
    REVIEWING,      // 回顾复盘
    COMPLETE,       // 完成
    FAILED,         // 失败
}
```

**状态流转**：
- IDLE → PLANNING：用户发送新任务
- PLANNING → EXECUTING：规划完成，开始执行
- EXECUTING → VERIFYING：工具执行完成，验证结果
- VERIFYING → EXECUTING：验证失败，重新执行
- VERIFYING → REVIEWING：验证通过，回顾复盘
- REVIEWING → COMPLETE：复盘完成
- 任意阶段 → FAILED：致命错误

**改动位置**：
- `ChatViewModel.kt` — 新增 `_workflowPhase` StateFlow
- UI 层 — 阶段指示器组件

### A.4 阶段 A 验收标准

- [ ] 长任务（>200 turn）可自动续跑，无需用户手动点 Continue
- [ ] 续跑次数达到上限后自动停止
- [ ] 应用重启后，未完成的深度任务可恢复续跑
- [ ] 多个独立工具调用可并行执行，效率提升可观测
- [ ] WorkflowPhase 状态随任务推进正确流转
- [ ] 顶部状态栏显示当前阶段

## 六、阶段 B：P0 + P1 能力移植（核心认知）

> **目标**：移植 8 项核心认知能力（5 项 P0 纯提示词 + 3 项 P1 客户端逻辑），实现深度模式"能用"的基础体验。

### B.1 深度模式总开关

**新增配置**：
- `deepModeEnabled` — 会话级布尔开关，持久化到 DB
- 默认关闭，用户手动开启

**改动位置**：
- `ChatSessionEntity` — 新增 `deep_mode_enabled` 字段
- `ChatViewModel.kt` — 新增 `_deepModeEnabled` StateFlow
- 斜杠菜单 — 新增 `/deep` 命令切换开关

### B.2 P0 档：5 项纯提示词注入

**实现方式**：在系统提示词中追加 `deepModeFragment`，仅当 `deepModeEnabled == true` 时注入。

| 编号 | 能力 | 注入位置 | 移植难度 |
|------|------|---------|---------|
| C1 | 三层意图解码 | deepModeFragment | 🟢 极低 |
| C2 | 反向验证 | VerifyGate 验证提示词 | 🟢 极低 |
| C3 | 第一性原理推导 | deepModeFragment | 🟢 极低 |
| C4 | 主动风险预判 | deepModeFragment | 🟢 极低 |
| C5 | 失败三次换方法 | GoalRunner 续跑逻辑 | 🟡 低 |

**实现要点**：
- 直接复用 iOS 的 deepModeFragment 文本（英文提示词，跨平台通用）
- 在 `buildSystemPrompt()` 末尾追加，受 `deepModeEnabled` 守卫
- C5 需要修改 GoalRunner 的续跑逻辑：连续失败 3 次后注入换策略指令

### B.3 P1 档：3 项客户端逻辑

| 编号 | 能力 | 实现方式 | 移植难度 |
|------|------|---------|---------|
| C6 | 心跳自检协议 | runAgentLoop 加计数器，每 5 次工具调用注入自检指令 | 🟡 低 |
| C7 | 任务后复盘 | WorkflowPhase 回到 COMPLETE 时触发复盘钩子 | 🟡 低 |
| C8 | 联网查询进攻 | send() 入口检测不确定标记词，追加查证指令 | 🟡 低 |

**C6 心跳自检**：
```kotlin
// 在 runAgentLoop 的工具执行后检查
heartbeatToolCallCount++
if (deepModeEnabled && heartbeatToolCallCount % 5 == 0) {
    // 注入自检指令
    injectHeartbeatSelfCheck()
}
```

**C7 任务后复盘**：
```kotlin
// WorkflowPhase 进入 COMPLETE 时触发
suspend fun maybeRunRetrospective() {
    if (!deepModeEnabled) return
    // 注入复盘提示词
    // 结果写入记忆系统
}
```

**C8 联网查询进攻**：

## 八、阶段 D：子智能体 + 后台优化（高级功能）

> **目标**：移植子智能体系统 + 针对 Android 平台特性做后台保活和性能优化，实现高级功能的完整体验。

### D.1 子智能体系统

**新建文件**：
- `agent/SubagentSession.kt` — 子智能体会话
- `agent/SubagentManager.kt` — 子智能体管理器
- `tools/TaskDispatchTool.kt` — task_dispatch 派发工具

**核心功能**：
1. 主智能体可通过 `task_dispatch` 工具派发子任务给子智能体
2. 每个子智能体有独立的上下文和工具集
3. 子智能体并行执行，结果汇总给主智能体
4. 子智能体卡片 UI 展示

**依赖**：
- 并行工具执行（阶段 A）
- WorkflowPhase 状态机（阶段 A）

### D.2 后台保活优化

**Android 特有问题**：
- Doze 模式：设备空闲时限制网络和 CPU
- 应用待机：长时间未使用的应用被限制
- 后台耗电：高功耗应用可能被系统杀死
- 内存压力：低内存时后台进程被清理

**优化方案**：

1. **前台服务强化**
   - 深度模式运行时启动前台服务
   - 持久化通知显示进度
   - 用户可通过通知快速返回应用

2. **断点续跑机制**
   - 深度任务的中间状态持久化到 DB
   - 被系统杀死后，重启应用可恢复任务
   - 从最近的检查点继续执行

3. **电量友好策略**
   - 电池电量 < 20% 时自动暂停深度任务
   - 仅充电时执行长任务（可配置）
   - 预估运行时间超过 10 分钟时提醒用户

4. **Wake Lock 管理**
   - 深度模式运行时持有 Partial Wake Lock
   - 防止 CPU 休眠导致任务中断
   - 任务完成或暂停时立即释放

### D.3 性能优化

**内存优化**：
- 深度模式下更积极的 context offload
- 工具结果增量持久化，不全量驻留内存
- 大输出的工具结果自动截断 UI 展示

**设备分级**：
- 根据设备内存、CPU 性能自动调整深度模式上限
- 低端机：限制最大续跑次数、禁用并行工具
- 高端机：全功能开放

**UI 性能**：
- 深度模式 UI 组件模块化，避免 ChatScreen 进一步膨胀
- Compose remember / derivedStateOf 优化重组
- 长列表的 LazyColumn 性能优化

## 九、风险评估与缓解策略

### 9.1 高风险（🔴）

#### 风险 1：性能与内存压力

**描述**：深度模式意味着更长的 agent loop、更多工具调用、更大上下文。Android 设备碎片化严重，低端机（如 2-3GB 内存）可能 OOM。

**证据**：
- T307 优化：DeepSeek V4 长文本在 Pixel 4a (256MB 堆) 上已出现 OOM
- 当前 MAX_AGENT_TURNS = 200，深度模式可能需要提高到 500+
- 更多 turn → 更多历史消息 → 更大内存占用

**影响**：
- 低端设备深度模式不可用或频繁崩溃
- 用户体验差

**缓解策略**：
1. 设备性能分级：根据内存/CPU 自动调整深度模式上限
2. 积极的 context offload：工具结果尽早 offload 到磁盘
3. 增量持久化：中间状态逐步写入 DB，不全量驻留内存
4. 低端机默认禁用深度模式，用户手动开启时警告

#### 风险 2：后台保活可靠性

**描述**：Android 后台限制比 iOS 严格得多，深度模式长任务容易被系统杀死。

**影响**：
- 深度任务频繁中断
- 用户信任度下降
- 与 iOS 体验差距明显

**缓解策略**：
1. 前台服务 + 持久化通知（必须）
2. 断点续跑机制（核心保障）
3. Wake Lock 持有
4. 电量优化白名单引导
5. 预估运行时间，超过 5 分钟提醒用户保持前台

#### 风险 3：工具循环检测误判

**描述**：深度模式的核心就是多轮迭代思考和工具调用，可能被 ToolLoopDetector 误判为死循环而熔断。

**影响**：
- 深度模式被提前中断
- 用户困惑为什么任务停了

**缓解策略**：
1. 深度模式下提高循环检测阈值（警告 10→20，熔断 30→50）
2. 增加"有进展的迭代"判断逻辑（工具输出有新内容则不算循环）
3. 深度模式下的迭代单独计数，不与普通模式共享计数器

### 9.2 中风险（🟡）

#### 风险 4：并行工具执行复杂度

**描述**：Android 端目前是纯串行工具执行，改并行涉及并发控制、资源竞争、错误处理等复杂问题。

**影响**：
- 开发周期可能超出预期
- 可能引入并发 bug

**缓解策略**：
1. 第一版只做"独立工具并行"，有依赖关系的保持串行
2. shell_execute 默认串行（沙箱限制），文件操作并行
3. 充分的并发测试

#### 风险 5：状态一致性与持久化

**描述**：GoalRunner + WorkflowPhase + DeepModeLevel 引入了多个新状态维度，持久化和恢复的复杂度增加。

**影响**：
- 应用重启后状态丢失或不一致
- 边界情况 bug

**缓解策略**：
1. 设计统一的会话状态持久化 schema
2. 状态变更的原子性保证
3. 充分的边界测试（杀进程恢复、网络中断恢复等）

#### 风险 6：双端维护成本

**描述**：深度模式功能需要 iOS 和 Android 各维护一套，后续迭代成本翻倍。

**影响**：
- 新功能上线慢
- 双端行为不一致的 bug

**缓解策略**：
1. 提示词和认知逻辑尽量共享（纯文本逻辑）
2. 建立双端对齐的测试用例集
3. 重大变更先在 iOS 验证，再移植 Android

### 9.3 低风险（🟢）

#### 风险 7：系统提示词膨胀

**描述**：深度模式增加的提示词会增加 token 消耗。

**缓解**：仅在深度模式启用时注入，平时不增加开销。

#### 风险 8：UI 复杂度膨胀

**描述**：ChatScreen.kt 已有 6500+ 行，新增深度模式 UI 可能进一步恶化。

**缓解**：深度模式 UI 模块化到独立文件，通过组合方式接入。
